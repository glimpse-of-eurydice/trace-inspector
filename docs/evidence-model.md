# Evidence Model

Trace Inspector separates claims by how strongly they are supported. A claim's
evidence level describes where the claim came from; it does not describe how
important or persuasive the claim sounds.

## 1. Observed claims（直接观测到的事实）

An observed claim is supported by an event or artifact that the runtime or
filesystem actually recorded.

Examples:

- The runtime recorded that `npm test` ended with exit code `1`.
- The runtime emitted three distinct plan updates during the turn.
- A `fileChange` event or `git diff` shows that `README.md` changed.
- The turn ended with status `completed`.

Important boundary:

> “Codex emitted a final summary saying that it edited `README.md`” is
> observed. “Codex really completed everything claimed in that summary” is not
> established until the underlying tool, file, or diff evidence is checked.

“Observed” does not mean only something a human can see with their eyes. It
means that the claim can be traced to a recorded runtime event or inspectable
artifact.

## 2. Model-reported claims（模型自述或模型报告的内容）

A model-reported claim comes from text generated by the model about its plan,
reasoning, confidence, interpretation, or completed work.

Examples:

- A reasoning summary says, “I will inspect the latest experiment file.”
- The final response says, “I updated the conclusion using the latest results.”
- The model says that it is highly confident in an answer.

A model-reported intention and an observed action must remain separate:

```text
Model: “I will search the official documentation.”
    → model-reported intention

Runtime: a web-search tool call was executed.
    → observed action

Model: “The search results support my conclusion.”
    → model-reported interpretation

Analyzer: the cited result appears relevant to the conclusion.
    → inferred or evaluated claim
```

Reasoning summaries exposed by an agent product are not assumed to be the
model's complete or private chain of thought.

## 3. Inferred claims（根据证据推断的判断）

An inferred claim is produced by relating one or more observed events under an
explicit analysis rule. It must link back to its evidence and use appropriately
limited language.

Examples:

- A command failed and was followed by a highly similar command, so the second
  command may be a retry.
- A file read failed and a new plan appeared afterward, so the agent may have
  changed strategy.
- The latest results could not be read and an archived summary was read next,
  so the final response may rely on stale evidence.

The component events can be observed while the relationship remains inferred:

```text
Observed: the file read failed.
Observed: a different plan was emitted afterward.
Inferred: the failure caused the strategy change.
```

Temporal order alone does not establish causation.

## 4. First observable divergence

The first observable divergence is the earliest material difference found by a
specified trace-alignment and comparison policy.

It is weaker than “the cause of the final-answer difference” because:

- many later processes can contribute to the final answer;
- uncontrolled model sampling or runtime scheduling can also differ;
- the alignment policy determines what counts as the first material difference;
- an unobserved internal difference may have occurred earlier.

Therefore:

```text
first observable divergence
    ≠ first internal divergence
    ≠ causal origin
```

Safe wording:

> The first observable difference under comparison policy X occurred at the
> result-file read. Later execution and final output also differed.

Unsafe wording:

> The result-file read caused the final answer to change.

## 5. Evidence requirements for findings

Every diagnostic finding should eventually contain:

- an evidence level: `observed`, `model_reported`, or `inferred`;
- the event or artifact identifiers supporting it;
- the deterministic rule or model prompt that produced it;
- limited wording appropriate to the evidence level;
- a way for the user to inspect the raw evidence.
